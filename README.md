# まいにちの台所

家族のレシピ・今週の献立・お店別の買い物リストをまとめる、日本語のスマートフォン向けWebアプリです。Next.js App Router / TypeScript / Tailwind CSS / Supabaseを使用します。有料APIは使用しません。

## 使える機能

- **レシピ帳**：追加・編集・削除、料理名・食材検索、家族ウケ度★1〜5、作り方メモ、基準人数と食材の分量・単位・カテゴリ。人数の初期値は4人、人数に応じた換算に対応。
- **材料の一括貼り付け**：登録・編集画面の「材料をまとめて貼り付ける」で、YouTubeの概要欄や料理サイトの複数行の材料を解析。分数・全角数字・大さじ／小さじ・少々／適量、箇条書き・A/Bの記号・材料見出しに対応し、人数は選択できる候補として表示します。解析はブラウザ内のルールのみで行い、外部AI API・有料サービスは使用しません。
- **今週の献立**：レシピから複数選択、同じ料理の重複選択、料理ごとの人数・調理チェック。5〜6品を目安に、品数の強制制限はありません。
- **週の切り替え**：今週の献立と買い物を履歴に保存し、未調理の料理・未購入の商品だけを引き継ぎます。履歴は自動削除しません。
- **買い物リスト**：お店別の「買うもの」と開閉できる「完了済み」で管理。チェックで完了済みへ移動し、外すと買うものへ戻ります。手動商品も献立からの自動生成品も、完了済みのゴミ箱から確認後に完全削除できます。食材名・単位の合算、お店・カテゴリ変更、手動追加も維持します。
- **完了済みの一括削除**：「完了済み」見出し右側のゴミ箱「一括削除」で、選択中の店舗の購入済み商品だけを削除します。「すべて」では全店舗、「お店未定」では未設定の商品だけが対象です。件数・対象店舗を確認し、キャンセルすれば何も変わりません。未購入品と個別削除ボタンは残ります。完了済みが0件のときと保存中は一括削除を無効にします。
- **買い物の初期店舗**：新しく追加する自動生成の材料・手動商品はカネスエに振り分けます。設定画面で別のお店や「お店未定」に変更できます。既存の商品は振り替えず、個別に変更した店舗や「お店未定」は再計算・人数変更・翌週引き継ぎでも保持します。
- **店舗管理**：カネスエ・業務スーパー・100均・コストコを初期登録。追加・編集・削除に対応。店舗削除後も商品は残ります。
- **永続保存**：Supabase Authによるメール・パスワード認証、確認メール、パスワード再設定、RLS。アカウントごとにDBへ自動保存。同一アカウントで別端末から利用できます。
- **スマートフォン対応**：画面下のナビ、大きな購入チェック、PWA、ホーム画面用アイコン、安全領域への対応。
- **準備と保管**：接続前の設定ガイド、保存しないサンプルモード、JSONによるデータ書き出し。

## 初めての設定

**[日本語セットアップガイド](docs/SETUP.md) に、初回設定から公開までの手順があります。**

```sh
npm ci
cp .env.example .env.local
```

1. Supabaseの無料プロジェクトを作成します。
2. SQL Editorで [supabase/schema.sql](supabase/schema.sql) を全て実行します。
3. `.env.local` にプロジェクトURLと公開用Publishable keyを設定します。

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://your-project.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=your-publishable-key
```

4. Supabase AuthenticationのSite URLとRedirect URLsに `http://localhost:3000` を設定します。
5. `npm run dev` を実行し、`http://localhost:3000` を開きます。
6. 新規登録して確認メールを開き、ログインします。

公開用キーはRLSと組み合わせてブラウザで使うためのキーです。**Secret key / service_role key / DBパスワードを環境変数に設定しないでください。** 従来の公開用 `NEXT_PUBLIC_SUPABASE_ANON_KEY` も読み込めますが、新規設定は上記を推奨します。

環境変数が未設定でもガイドとサンプルモードを開けます。サンプルはメモリ内だけで動作し、再読込・終了で消えます。本番データとは混ざりません。

## 開発・検証

Node.js 22以上、npmを使用します。

```sh
npm run typecheck
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

Linuxで既存のChromiumを使用する場合：

```sh
PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=/usr/bin/chromium npm run test:e2e
```

テストは献立の重複・換算・買い物の状態保持・週切替・履歴、実際のSQLをPostgreSQL互換環境（PGlite）で実行するRLSと競合制御、スマホ幅のブラウザ操作とPWAを確認します。GitHub Actionsでも型・テスト・ビルド・ブラウザテストを実行します。

### 材料をまとめて登録する

1. 新規登録またはレシピ帳の編集画面の「材料をまとめて登録」で、材料一覧を入力欄に貼り付けて「材料を解析する」を押します。URLからの自動取得は行いません。`玉ねぎ 1/2個` のほか、食材名の次の行が `1/2個` のような分量だけになるコピー形式、`しょうゆ 大さじ：2` にも対応します。
2. 原文付きの一覧で食材名・分量・単位・カテゴリを修正します。判定できない行も削除せず「要確認」で残ります。未入力を修正し、要確認の行は確認済みにしてください。追加不要な行はチェックを外せます。
3. 人数候補は、選んだときだけ基準人数に反映します。材料の分量は原文のままです。「2〜3人分」などは複数候補として扱います。
4. 「確認した○行を食材欄に追加」で既存行の末尾に追加します。同名・同単位の行も上書き・合算せず、重複の確認を求めます。新規レシピの最初の未入力の仮行だけは置き換えます。既存レシピの行は変更・削除しません。食材は既存分を含め100行までで、超えた分を黙って切り捨てることはありません。
5. 従来の個別入力でも調整でき、最後の「レシピを保存」で既存のSupabase保存処理を使います。未追加の貼り付け内容がある場合は、追加または破棄するまで保存を止めます。解析・修正・食材欄への追加だけではDBへ書き込みません。

解析は一般的な表記の補助です。範囲・複数食材の一行記載・補足分量などは原文を確認して修正してください。「少々」「適量」などは既存形式に合わせて分量1・単位「少々」「適量」として扱い、人数換算・買い物集計も数値として行います。未知のカテゴリは「その他」です。見出しとして扱った行も一覧で確認できます。保存形式・DBスキーマ・買い物集計の仕組みは変わりません。

## データ保存の仕組み

- 各アカウントの状態を `planner_data` のJSONB文書1行へ保存します。レシピ・献立・買い物・履歴を一括保存するので、週切替の途中だけが保存されることを防ぎます。
- `save_planner` RPCはログイン中の `auth.uid()` を使います。RLSが別アカウントの参照・書換えを拒否します。
- 保存時に `revision` の一致を確認します。別端末で先に更新された場合は保存を拒否し、再読込を案内します。操作は最新データでやり直してください。無断で古い文書を上書きしません。
- 保存成功後に画面へ反映します。通信失敗時は保存完了と表示せず、再読込による確認を案内します。
- 献立にはレシピの登録時点の写しを持ちます。レシピ帳を編集・削除しても、献立と履歴は変わりません。
- 自動集計と手動追加を区別し、献立の再計算で手動商品を消しません。同じ食材でも手動追加した商品は別行です。
- 完了済みの自動生成品を削除すると、その時点の献立ごとの必要量を既存の `meal.stocked` に購入済みとして記録し、買い物の行を削除します。同じ献立の再集計や翌週への引き継ぎでは復活せず、新しい献立・購入済み量を超える増員分は未購入品として追加します。手動商品の削除では献立の在庫を変更しません。削除は保存成功後に反映し、キャンセルや保存失敗では商品を残します。
- 個別削除と一括削除は同じ関数を使い、確認画面を開いた時点の商品IDだけを削除します。確認後に未購入へ戻された商品・対象店舗から移動した商品・消えた商品があれば全件を中止します。新しく完了済みになった商品を無断で追加しません。一括削除も既存の保存RPCを1回だけ実行し、失敗時は買い物の行と購入済みの記録を両方保持します。削除の副作用で未選択の商品を再集計・統合・削除しません。
- 完了済みを削除しても、レシピ帳・献立の内容・既存の履歴は削除しません。人数を減らして戻しても購入済みの範囲内では再購入しません。完全削除後はチェック解除による復元ができないため、商品名と分量を表示して確認します。削除には既存の `checked` と `stocked` を使います。
- 買い物の初期店舗はJSON文書の任意項目 `defaultStoreId` に店舗IDで保存します。設定がない旧データは、既存のカネスエを新規商品の初期店舗に使います。カネスエが削除済みなら店舗を作り直さず「お店未定」とし、既存の商品は変更しません。初期店舗を削除すると設定も「お店未定」になり、店名を変更してもIDによる設定は保持します。完全削除後に増員等で生じる不足分は新しい商品として現在の初期店舗へ追加します。保存先テーブル・RPC・schemaVersionは維持し、SQLの再実行やデータ移行は不要です。
- 翌週へ持ち越す未調理料理の購入済み食材は、購入済みの分量として記録します。再購入を防ぎ、人数を増やしたときだけ不足分を追加します。調理済み料理の未購入食材も持ち越します。
- チェック済みの自動食材が増量されたら、買い忘れ防止のためチェックを外します。数量は小数点以下4桁まで丸め、単位変換（gとkg、大さじとml等）は行いません。「適量」は数量1・単位「適量」として登録できます。
- アプリの家庭データはlocalStorageへ保存しません。Supabase SDKがログイン状態を維持するためにブラウザへ保存する認証セッションは別です。
- PWAは公開アイコンとオフライン案内のみキャッシュします。認証済みHTML・家庭のデータ・Supabase APIはキャッシュしません。保存・読み込みには通信が必要です。

詳しい設計・実機での確認項目は [docs/OPERATIONS.md](docs/OPERATIONS.md) を参照してください。
