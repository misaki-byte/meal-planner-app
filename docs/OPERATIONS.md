# 設計・動作確認・運用

## データと認証

`planner_data.user_id` は `auth.users.id` を参照します。アプリの家庭データは1アカウント1行のJSONBです。毎回、文書全体をSQL関数 `save_planner` で更新します。献立の履歴・買い物の履歴を1つのトランザクションで確定し、同時更新にはrevisionによる楽観的ロックを使用します。

RLSは `authenticated` に対して `auth.uid() = user_id` のselect/insert/updateだけを許可します。anonはテーブルも関数も使用できません。関数はSECURITY INVOKERでRLSを適用し、呼出側から任意のuser_idを受け取りません。service_roleは不要です。

Supabaseへの通信はブラウザのSDKから行います。Next.js側でアカウントのデータをSSR・共有キャッシュしません。認証セッションの保存はSupabase SDKに任せ、レシピ等をlocalStorageへ保存する実装はありません。ログアウト時は表示データを破棄します。

## 週切替と自動食材

1. 現在の献立（レシピの写し・人数・調理状態）と買い物リストを履歴へコピーします。
2. 未調理料理だけを次週へコピーします。
3. 未調理料理のうち購入済みの食材について、その料理に必要な購入済み数量を記録します。
4. 調理済み料理に関係する未購入分は、買い物の持ち越し数量として保持します。
5. 未購入の手動商品は保持し、購入済みの手動商品は今週のリストから除きます。履歴には残ります。
6. 次週の料理の不足分と持ち越し分を集計します。料理の重複・週切替の繰り返しで二重計上しません。

食材名と単位はUnicode NFKC・前後空白・連続空白・英字大小を正規化して比較します。カテゴリやお店が異なっていても、同じ自動食材は1行です。手動商品は独立しているので、献立更新によって消えません。

レシピ帳を編集しても登録済み献立の食材は変わりません。献立を新しい内容にするには古い料理を献立から外し、もう一度追加してください。過去のレシピ内容は履歴に残ります。

週は月曜始まり、切替は現在の週から7日後へ手動で進めます。自動リセットはしません。履歴は自動で間引きません。JSON文書には安全上20MBの上限があります。家庭での通常利用向けで、上限を超える場合は履歴別テーブルなどへの移行が必要です。

## 検証方法

- `npm run typecheck`：TypeScriptの型整合性。
- `npm test`：数量・同じレシピの重複・購入チェックと手動商品の保持・週切替・購入済み食材の再追加防止・店舗削除など。
- DBテストでは `supabase/schema.sql` 自体をPGliteで実行。アカウントA/Bと匿名ロールを作り、他人のデータを読めない・変更できないこと、旧revisionを拒否することを検証。
- `npm run build`：環境変数なしでも案内画面をビルドできること。
- `npm run test:e2e`：本番ビルドを起動して、スマホ幅のChromiumで操作。献立重複追加、数量合算、手動商品、購入チェック、翌週の履歴、レシピCRUD・検索・換算、店舗CRUD、PWAのオフライン案内を検証。
- 追加の認証テストでは実際のSupabase SDKを動かし、通信先だけをPlaywrightのローカル応答へ置き換えます。保存・再読込・別ブラウザでの復元・競合拒否・ログアウト・アカウント切替を確認します。本物のSupabaseへ接続しません。

認証ブラウザテストの実行方法（ダミー値をビルド時だけ指定）：

```sh
NEXT_PUBLIC_SUPABASE_URL=https://e2e-placeholder.supabase.co NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=e2e-public-placeholder npm run build
E2E_AUTH=1 npm run test:e2e
```

実行後、通常の `npm run build` で実際の接続設定に戻します。GitHub Actionsは未接続と認証モックの両方を検証します。

これらは実際のSupabaseプロジェクトのメール配信・公開URL・iOSのインストール挙動を代替しません。ご自身のプロジェクトの接続後は以下を確認してください。

## 接続後の最終確認

- パソコンで新規登録 → 確認メール → ログイン → レシピ作成。
- 同じアカウントでスマホからログインし、保存内容が見える。
- 一度アプリを閉じ、開き直してデータが残っている。
- 別アカウントBでログインし、Aのレシピ等が見えない。
- 2端末で同時に開き、片方で更新した後、もう片方の古いデータの保存が競合として拒否される。
- 買い物チェック、手動商品、お店変更を保存し、別端末の再読込で一致する。
- 作った料理／未調理料理／購入済み／未購入を用意して週切替。履歴と持ち越しが合っている。
- パスワード再設定メールのリンクから新しいパスワードを設定できる。
- 公開後、iPhone/Androidでホーム画面追加を確認する。

## バックアップと復元

設定の「データを書き出す」はレシピ・献立・買い物・履歴を含むJSONファイルをダウンロードします。内容を失わないため、端末の外にも控えを保存してください。

UIには誤上書きを避けるためのインポートボタンを設けていません。復元が必要な場合は、まず現在の文書をSupabase Dashboardから書き出し、バックアップJSONが `src/lib/model.ts` の `stateSchema` に合うことを確認してください。保守作業として認証済みクライアントから `save_planner` を最新revisionとともに呼び出せます。接続情報やservice_roleをファイルへ混ぜないでください。

アカウント削除をSupabaseで実行すると、そのユーザーの文書も外部キーのON DELETE CASCADEで削除されます。ログアウトとは異なります。アカウント削除が必要なときは、先に書き出した控えを保管してください。
